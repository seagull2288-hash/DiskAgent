# 轮盘智能体第四阶段：批次反馈进入下一批优化请求

日期：2026-11-05。本阶段把评价模块的结构化事实送入原优化中心请求，并保存“输入反馈—搜索假设—后续实测结果”的对应关系。

## 已完成的闭环

```text
原控制器提交本批真实结果
  → 结果分析（应力、位移、近似截面积、约束状态）
  → 有来源、版本和ID的批次反馈
  → 下一批原中心请求的 batch_feedback 输入
  → LLM返回原有 center / rationale / candidate_type
  → 原Python采样与筛选、原Workbench评价
  → 更新该决策的后续实测结果
```

它补充了原提示词已有的历史数值输入，不改变固定应力目标、九参数含义、变量边界、工程载荷、原采样尺度规则或模型输出格式。统计判断由程序完成，LLM理由仍视为搜索假设，不当作热点、因果或工程合格性证据。

## 从工作台使用

启动方式与上一阶段相同：双击 `start_disk_agent.cmd`，或运行 `python -B -m agent_app --app`，打开 `http://127.0.0.1:8765/`。

新建的中心搜索工作流默认启用结构化反馈。先预览、再显式开始真实计算。选中工作流，在“批次反馈与决策”页签查看：

- 反馈ID、来源已提交候选数及实测摘要；
- 该批中心、程序采样尺度与模型搜索假设；
- 本批后续实测改善、实际提交数量及评价状态；
- 缓存复用、原始来源工作流及追溯文件。

已存在的旧工作流保持原策略，不自动升级正在执行的决策语义。历史run的只读分析不会补造反馈记录。原始缓存没有结构化反馈证据时，页面显示 cached_legacy；若复用其他新工作流的已生成中心，则保留原反馈ID和来源工作流。

如果希望用当前4候选运行做最小真实联调，可在新任务中选择该run作上下文，输入“再算1个候选”，预览后确认目标总数为5，再显式开始。它会在下一批中心请求使用已有4个候选反馈，通常新增1次中心请求和1次候选评价，不重复基准。原工作流总预算不因此改变。

本次开发没有启动这次真实追加。需要新建工作流的原因是已完成工作流预算固定；同一物理run仍可继续使用。

## 文件职责

| 文件 | 职责 |
|---|---|
| `agent_app/feedback.py` | 纯函数构造和严格校验批次反馈；生成可复核ID及受限提示词摘要 |
| `agent_app/feedback_search.py` | 通过原SearchProposer的client_factory扩展注入输入、核验缓存来源、保存决策与后续结果 |
| `agent_app/tools.py` | 接收内部feedback上下文和决策回调；在FEA前补审缓存候选 |
| `agent_app/supervisor.py` | 冻结反馈策略版本，持久化决策轨迹，批次结束或中断时更新实测结果 |
| `agent_app/state.py` | feedback_policy、decision_trace兼容存储 |
| `agent_app/static/index.html` | 反馈与决策页签；把实测、模型假设、缓存及结果分开显示 |

`python_control`及原API桥不需要修改。原求解断点指纹继续生效；反馈适配器另有代码版本签名。适配逻辑变化后，未完成的新反馈工作流会拒绝悄悄改变策略，可在审核后新建工作流继续同一个兼容物理run。普通TaskSpec未新增模型权限、物理配置或任意路径字段。

## 反馈单内容与真实性

完整反馈使用 `disk-agent.batch-feedback.v1`：包含workflow/run、代次、来源历史签名、来源窗口、基准/当前/历史最优、最多3条近期实测、已实现规则、工程未知项、冻结总体预算和短程序建议。feedback_id由规范内容SHA256生成。

输入中的应力、位移和面积来自已提交记录。原生证据在生成反馈时重新检查；读取的历史必须与该中心的basis_history完全一致。没有实测依据时不生成“某尺寸导致应力下降”等结论。

提示词版去掉长绝对路径和冗余证据，保留ID和事实摘要。完整反馈限制14000字符，提示词摘要限制6500字符，超限报错，不静默截掉约束或改变事实。该限制不是供应商token计费上限。

许用应力、质量和寿命等未实现约束继续为unknown/not_assessed。近似截面积不等于质量；参数重要性、单变量梯度、应力热点、Sobol/Shapley知识没有被本阶段凭空生成。

## 成本和缓存

默认仍是一批最多4个候选共享一个中心请求。本阶段没有独立的反思API调用。反馈摘要会增加输入token；实际费用以供应商usage为准。原HTTP重试与提案纠错仍可能增加请求次数。

模型实际收到的原始HTTP body、落盘prompt与反馈引用要一致。缓存plan/center/成功回答可恢复时，不重新请求模型、不改写已缓存计划。缓存批次中途丢失必要中心证据时，拒绝盲目重建新中心。对比来源错误、代次错误、历史签名错误或缺失引用的增强提示词，也会在候选FEA前停止。

为防进程恰好在审计写入中断，候选先在短名私有暂存目录生成；反馈来源、决策文件及工作流状态都保存后，才把candidate.json原子发布到控制器可恢复路径。控制器直接复用pending候选时，FEA入口仍会核验决策。失败恢复不会通过缓存绕过审计。

```text
python_llm_runs/run_.../search/generation_002/center_api/request_.../proposal_01/
    prompt.json         实际发送的增强提示词
    request.json        原HTTP请求body（脱敏）
    response.json       原响应及usage
    answer.json         模型文本与元数据
    feedback_ref.json   反馈文件、摘要和提示词签名
```

成本仍只统计原始center_api请求目录；候选副本及暂存选择文件不重复计费。decision的request_status表示该工作流是否首次记录了该批原始请求；cache_reused表示当前选择复用了已存中心，两者不等同刷新页面或新发HTTP。

最后一批可能只授权部分缓存候选，例如6候选按4+2执行。决策仍保存完整的4候选缓存计划，但后续结果按本工作流授权的2候选判断完成，不误标为中断，也不自动补算到8。
